# HU-01 · Especificación comparativa ISO/IEC/IEEE 29148:2018

El agricultor necesita una cuenta para ofrecer sus productos. Esta especificación reescribe la historia en términos verificables y compara su alcance con el [backlog](../BACKLOG.md) y la [trazabilidad BDD](trazabilidad-bdd.md).

## Identificación y alcance

La tarea [DOC #133](https://github.com/Angel-uniajc/AgrovalleConnect/issues/133) documenta el registro de agricultores. La línea base técnica es `develop` en `b1090a05439ad5152087f47dfb1967b1671d585e`. La especificación utiliza requisitos identificados, prescriptivos y verificables para la comparación solicitada con ISO/IEC/IEEE 29148:2018.

El actor es un agricultor sin cuenta. La entrada es una petición HTTP pública con `Content-Type: application/json`. La operación crea un usuario y su perfil de agricultor mediante un servicio transaccional.

## Contrato de entrada y salida

El sistema deberá validar las siguientes restricciones antes de crear la cuenta.

| Campo JSON | Restricción |
|---|---|
| `nombre` | Obligatorio, no vacío y de máximo 50 caracteres. |
| `ubicacion_valle` | Obligatorio, no vacío y de máximo 15 caracteres. |
| `cedula` | Obligatoria y compuesta por entre 6 y 10 dígitos. |
| `correo` | Obligatorio, de máximo 50 caracteres y conforme a la expresión de formato definida en `RegistroAgricultorRequest`. |
| `password` | Al menos 8 caracteres, con mayúscula, minúscula, dígito y un símbolo de `@$!%*?&`. Solo se admiten letras ASCII, dígitos y esos símbolos, conforme al validador implementado. |

La respuesta exitosa deberá contener los campos públicos `nombre` y `mensaje`. Los errores de validación deberán responder `400` con los campos rechazados. El mapeo existente usa nombres Java, incluido `ubicacionValle`. Las colisiones de correo o cédula deberán responder `409`.

Las restricciones se contrastan con [RegistroAgricultorRequest](../src/main/java/com/agrovalleconnect/agrovalle_connect/dto/RegistroAgricultorRequest.java), [RegistroAgricultorResponse](../src/main/java/com/agrovalleconnect/agrovalle_connect/dto/RegistroAgricultorResponse.java) y [AuthController](../src/main/java/com/agrovalleconnect/agrovalle_connect/controller/AuthController.java).

## Requisitos y comparación BDD

| ID | Requisito prescriptivo | Given / When / Then | Verificación |
|---|---|---|---|
| REQ-01.1 | Cuando se envíe a `POST /api/v1/auth/register` un JSON válido con nombre, ubicación, cédula, correo y contraseña, con cédula y correo únicos, el sistema deberá persistir la cuenta de agricultor y responder `201 Created`. | Dado un agricultor sin cuenta, cuando envía datos válidos, entonces se crea el registro. | `AuthControllerIntegrationTest#registroExitoso_persisteYGuardaHashNoTextoPlano` |
| REQ-01.2 | Si faltan campos obligatorios o la cédula es inválida, el sistema deberá responder `400 Bad Request` e indicar los campos con error, sin crear una cuenta. | Dados datos incompletos o una cédula inválida, cuando se solicita el registro, entonces se rechaza la petición. | `registrarAgricultor_conCamposVacios_retorna400` y `registrarAgricultor_conCedulaInvalida_retorna400` |
| REQ-01.3 | Si la cédula ya está registrada, el sistema deberá responder `409 Conflict` y preservar el registro existente. | Dada una cédula registrada, cuando se vuelve a usar, entonces se rechaza el duplicado. | `rechazaCedulaDuplicada` y prueba de servicio de duplicidad |
| REQ-01.4 | Si el correo ya está registrado, el sistema deberá responder `409 Conflict` y preservar el registro existente. | Dado un correo registrado, cuando se vuelve a usar, entonces se rechaza el duplicado. | `rechazaCorreoDuplicado` |
| REQ-01.5 | Si la contraseña incumple las restricciones del contrato de entrada de este documento, el sistema deberá responder `400 Bad Request` sin crear una cuenta. | Dada una contraseña débil, cuando se solicita el registro, entonces se rechaza la petición. | `contrasenaDebil_devuelve400YNoGuardaNada` |
| REQ-01.6 | Al crear la cuenta, el sistema deberá almacenar la contraseña como un hash BCrypt y omitir la contraseña y su hash de la respuesta HTTP. | Dados datos válidos, cuando se crea la cuenta, entonces la credencial queda protegida y el cliente recibe únicamente los datos públicos de registro. | Revisar el servicio y el DTO de respuesta. La prueba de registro exitoso comprueba el hash persistido. |

Los métodos sin prefijo de clase pertenecen a `AuthControllerIntegrationTest`. El entorno de producción usa PostgreSQL. Las pruebas con H2 verifican el comportamiento de la aplicación y requieren una comprobación adicional para propiedades específicas de PostgreSQL.

El BDD describe el flujo desde la perspectiva del usuario. La redacción prescriptiva asigna identificadores a las reglas y precisa entradas, respuestas y efectos observables. El escenario principal del backlog enumera tres campos. La especificación explicita correo y contraseña porque el contrato implementado también los requiere. Los rechazos adicionales y el hash recogen controles de la implementación y su trazabilidad. La comparación conserva la HU original.
