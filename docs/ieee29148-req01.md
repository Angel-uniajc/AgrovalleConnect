# HU-01 · Especificación comparativa ISO/IEC/IEEE 29148:2018

El agricultor necesita una cuenta para ofrecer sus productos. Esta especificación reescribe la historia en términos verificables y compara su alcance con el [backlog](../BACKLOG.md) y la [trazabilidad BDD](trazabilidad-bdd.md).

## Identificación y alcance

La tarea [DOC #133](https://github.com/Angel-uniajc/AgrovalleConnect/issues/133) documenta el registro de agricultores. La línea base técnica es `develop` en `b1090a05439ad5152087f47dfb1967b1671d585e`. La especificación utiliza requisitos identificados, prescriptivos y verificables para la comparación solicitada con ISO/IEC/IEEE 29148:2018.

El actor es un agricultor sin cuenta. La entrada es una petición HTTP pública con `Content-Type: application/json`. La operación crea un usuario y su perfil de agricultor mediante un servicio transaccional.

## Partes interesadas

| Parte interesada | Necesidad en el registro |
|---|---|
| Agricultor | Crear su cuenta, recibir un resultado comprensible y proteger sus credenciales. |
| Administrador del sistema | Conservar la integridad de cuentas y perfiles y operar la aplicación con una configuración de persistencia y seguridad verificable. |
| Equipo de desarrollo y calidad | Mantener trazabilidad entre reglas, contrato REST y evidencias de verificación. |

## Contrato de entrada y salida

El sistema deberá validar las siguientes restricciones antes de crear la cuenta.

| Campo JSON | Restricción |
|---|---|
| `nombre` | Obligatorio, no vacío y de máximo 50 caracteres. |
| `ubicacion_valle` | Obligatorio, no vacío y de máximo 15 caracteres. |
| `cedula` | Obligatoria y compuesta por entre 6 y 10 dígitos. |
| `correo` | Obligatorio, de máximo 50 caracteres y conforme a la expresión de formato definida en `RegistroAgricultorRequest`. |
| `password` | Al menos 8 caracteres, con mayúscula, minúscula, dígito y un símbolo de `@$!%*?&`. Solo se admiten letras ASCII, dígitos y esos símbolos, conforme al validador implementado. |

La respuesta exitosa deberá contener los campos públicos `nombre` y `mensaje`. Los errores de validación deberán responder `400` con los campos rechazados. El mapeo existente usa nombres Java, incluido `ubicacionValle`. Las colisiones de correo o cédula deberán responder `409`.

Las restricciones se contrastan con [RegistroAgricultorRequest](../src/main/java/com/agrovalleconnect/agrovalle_connect/dto/RegistroAgricultorRequest.java), [RegistroAgricultorResponse](../src/main/java/com/agrovalleconnect/agrovalle_connect/dto/RegistroAgricultorResponse.java) y [AuthController](../src/main/java/com/agrovalleconnect/agrovalle_connect/controller/AuthController.java).

## Requisitos funcionales y trazabilidad

| ID | Requisito prescriptivo | Given / When / Then | Verificación |
|---|---|---|---|
| REQ-01.1 | Ante una petición válida según el contrato de entrada, con correo y cédula disponibles, el sistema deberá persistir la cuenta de agricultor. | Dados datos válidos, cuando se solicita el registro, entonces se crea la cuenta. | Prueba automatizada `AuthControllerIntegrationTest#registroExitoso_persisteYGuardaHashNoTextoPlano`. |
| REQ-01.2 | Ante la ausencia o el contenido en blanco de un campo obligatorio, el sistema deberá responder `400 Bad Request`. | Dados campos obligatorios vacíos, cuando se solicita el registro, entonces se rechaza la petición. | Prueba automatizada `registrarAgricultor_conCamposVacios_retorna400`. Inspección de `@NotBlank` en el DTO para campos ausentes. |
| REQ-01.3 | Ante una cédula que incumpla el formato de 6 a 10 dígitos, el sistema deberá responder `400 Bad Request`. | Dada una cédula inválida, cuando se solicita el registro, entonces se rechaza la petición. | Prueba automatizada `registrarAgricultor_conCedulaInvalida_retorna400` e inspección de `@Pattern` en el DTO para ambos límites. |
| REQ-01.4 | Ante una cédula ya registrada, el sistema deberá responder `409 Conflict`. | Dada una cédula registrada, cuando se vuelve a usar, entonces se rechaza el duplicado. | Prueba automatizada `rechazaCedulaDuplicada`. |
| REQ-01.5 | Ante un correo ya registrado, el sistema deberá responder `409 Conflict`. | Dado un correo registrado, cuando se vuelve a usar, entonces se rechaza el duplicado. | Prueba automatizada `rechazaCorreoDuplicado`. |
| REQ-01.6 | Ante una contraseña que incumpla el contrato de entrada, el sistema deberá responder `400 Bad Request`. | Dada una contraseña débil, cuando se solicita el registro, entonces se rechaza la petición. | Prueba automatizada `contrasenaDebil_devuelve400YNoGuardaNada` e inspección de `@Pattern` para la política completa. |
| REQ-01.7 | Tras crear la cuenta, el sistema deberá responder `201 Created`. | Dado un registro válido, cuando finaliza la creación, entonces se informa el éxito. | Prueba automatizada `AuthControllerIntegrationTest#registroExitoso_persisteYGuardaHashNoTextoPlano`. |
| REQ-01.8 | La respuesta de registro exitoso deberá exponer los campos públicos `nombre` y `mensaje`. | Dada una cuenta creada, cuando se devuelve la respuesta, entonces se informa el resultado público. | Inspección de `RegistroAgricultorResponse` y del mapeo de respuesta en `AgricultorMapper`. |
| REQ-01.9 | Ante una petición rechazada por validación o duplicidad, el sistema deberá preservar el número de cuentas. | Dados datos inválidos o duplicados, cuando se rechaza el registro, entonces se conserva el estado previo. | Pruebas automatizadas de rechazos en `AuthControllerIntegrationTest`, que comparan el número de usuarios y agricultores. |
| REQ-01.10 | Ante un error de validación, el sistema deberá identificar los campos rechazados mediante sus nombres Java. | Dados datos inválidos, cuando se informa el error, entonces se identifican sus campos. | Inspección del método `datosInvalidos` de `ManejadorErrores`. |
| REQ-01.11 | Ante el exceso de longitud de nombre, ubicación o correo, el sistema deberá responder `400 Bad Request`. | Dado un campo que supera su límite, cuando se solicita el registro, entonces se rechaza la petición. | Pruebas automatizadas de longitud de `RegistroAgricultorRequestTest` e inspección del flujo `@Valid` y su manejador de errores para el resultado HTTP. |
| REQ-01.12 | Ante un correo que incumpla el formato del contrato de entrada, el sistema deberá responder `400 Bad Request`. | Dado un correo inválido, cuando se solicita el registro, entonces se rechaza la petición. | Prueba automatizada `RegistroAgricultorRequestTest#correoSinFormato_esRechazado` e inspección del flujo `@Valid` y su manejador de errores para el resultado HTTP. |

Los métodos sin prefijo de clase pertenecen a `AuthControllerIntegrationTest`. El entorno de producción usa PostgreSQL. Las pruebas con H2 verifican el comportamiento de la aplicación y requieren una comprobación adicional para propiedades específicas de PostgreSQL.

El BDD describe el flujo desde la perspectiva del usuario. La redacción prescriptiva asigna identificadores a las reglas y precisa entradas, respuestas y efectos observables. El escenario principal del backlog enumera tres campos. La especificación explicita correo y contraseña porque el contrato implementado también los requiere. Los rechazos adicionales y el hash recogen controles de la implementación y su trazabilidad. La historia original HU-01 no se modifica en `BACKLOG.md`. Esta especificación la amplía sin alterarla.

## Requisitos no funcionales

| ID | Requisito | Verificación |
|---|---|---|
| RNF-01.1 · Seguridad | Al crear una cuenta, el sistema deberá almacenar la contraseña mediante un hash BCrypt. | Prueba automatizada `AuthControllerIntegrationTest#registroExitoso_persisteYGuardaHashNoTextoPlano`, que comprueba diferencia frente al texto original y `PasswordEncoder.matches`. Inspección del bean `BCryptPasswordEncoder` en `SecurityConfig` para el algoritmo. |
| RNF-01.2 · Confidencialidad | El sistema deberá omitir la contraseña y su hash de la respuesta de registro. | Prueba automatizada `AuthControllerIntegrationTest#registroExitoso_persisteYGuardaHashNoTextoPlano`, que verifica ausencia de `$.password` y `$.passwordHash` y del texto de la contraseña en el cuerpo. Inspección del DTO público de salida. |
| RNF-01.3 · Integridad | El sistema deberá crear el usuario y el perfil de agricultor dentro de una única transacción. | Inspección de `@Transactional` en `AgricultorRegisterService.registrar`. |

El tiempo máximo de respuesta queda por acordar con las partes interesadas. La línea base carece de un umbral de latencia y de pruebas de rendimiento que permitan establecer su aceptación.

## Restricciones y fuentes técnicas

- La línea base usa Java 25 y Spring Boot 4.1.1, declarados en [pom.xml](../pom.xml).
- La persistencia de producción usa PostgreSQL y entidades JPA. La prueba de integración usa H2, configurado en [application.properties de pruebas](../src/test/resources/application.properties).
- El contrato HTTP/JSON se publica mediante Spring Web, con Bean Validation y Spring Security. `SecurityConfig` permite el registro público y configura el codificador de contraseñas.
- La guía del segundo corte menciona Java 17. El equipo mantiene Java 25 LTS, versión declarada en `pom.xml` y usada por el CI, y deja constancia de esta decisión en el documento de entrega.

La inspección utiliza [AgricultorRegisterService](../src/main/java/com/agrovalleconnect/agrovalle_connect/service/AgricultorRegisterService.java), [AgricultorMapper](../src/main/java/com/agrovalleconnect/agrovalle_connect/mapper/AgricultorMapper.java), [SecurityConfig](../src/main/java/com/agrovalleconnect/agrovalle_connect/config/SecurityConfig.java) y [ManejadorErrores](../src/main/java/com/agrovalleconnect/agrovalle_connect/exception/ManejadorErrores.java).

La evidencia automatizada se encuentra en [AuthControllerIntegrationTest](../src/test/java/com/agrovalleconnect/agrovalle_connect/controller/AuthControllerIntegrationTest.java) y [RegistroAgricultorRequestTest](../src/test/java/com/agrovalleconnect/agrovalle_connect/dto/RegistroAgricultorRequestTest.java).
